Context

The native engine sets the budget of a call with wasm_runtime_set_instruction_count_limit (host-extism-plugins, ENG-4). WAMR holds the limit in a C int in three places: the field WASMExecEnv.instructions_to_execute, the local instructions_left of the interpreter, and the parameter of the function. Thus Budget::parse refuses a budget above 2147483647. The Morphir model line in finos/morphir-moonbit needs 5,000,000,000 instructions for one call on a large model.

The interpreter copies the limit into its local counter when a call enters it, and decrements only the local. A negative limit means no limit. When the local is 0, the call stops with the exception "instruction limit exceeded", which the stub maps to BudgetExhausted.

Goals and non-goals

  • Goal: a budget of at least 5,000,000,000 instructions, enforced exactly on native, on every platform and with every C compiler that builds the engine.
  • Goal: a small vendored patch that a new vendor run keeps, and that upstream can take.
  • Goal: the smallest API change. Budget::parse(Int64) keeps its signature.
  • Non-goal: a budget on js, a budget across calls or host re-entries, the classic interpreter, AOT and JIT.

AOT code reads some fields of WASMExecEnv by offset: module_inst, argv_buf, native_stack_boundary, suspend_flags, aux_stack_boundary, aux_stack_bottom and native_symbol. All of them come before instructions_to_execute, so a wider counter moves no field that AOT code reads. AOT and JIT do not read the counter.

Decisions

CNT-1. A 64-bit counter in the vendored WAMR (Owner)

The patch "64-bit instruction counter" in scripts/vendor-wamr.mbtx has five hunks:

  • core/iwasm/common/wasm_exec_env.h: int instructions_to_execute becomes int64.
  • core/iwasm/interpreter/wasm_interp_fast.c: int instructions_left becomes int64.
  • core/iwasm/include/wasm_export.h, core/iwasm/common/wasm_runtime_common.h and .c: a new function wasm_runtime_set_instruction_count_limit64.
WASM_RUNTIME_API_EXTERN void
wasm_runtime_set_instruction_count_limit64(wasm_exec_env_t exec_env,
                                           int64_t instruction_count);

The int function stays as it is, so the ABI does not change for other users of WAMR, for example language bindings that call it with a C int. It writes into the wider field, and the sign extension keeps -1 as "no limit". The engine builds the fast interpreter only (extism_config.h), and the vendor script copies no wasm_interp_classic.c, so the patch changes only the fast interpreter. A pull request to upstream also changes the same local in wasm_interp_classic.c and the comment of the API.

Alternatives: a refill with #4902 (not merged, see above); a host-side count across chunks (not possible: a call that reaches the limit cannot continue); a change of the int parameter to int64_t (smaller, but it breaks binary callers).

CNT-2. The budget range is 1 to the Int64 maximum (Owner)

Budget::parse accepts 1 to 9223372036854775807. The counter is a signed 64-bit integer and a negative value means no limit, so the engine can enforce every positive value. At about 1.4 × 109 metered instructions per second, the maximum is more than 200 years of run time, so a lower maximum protects nothing. A consumer that sends the budget through a JSON number or a JavaScript Number can set its own lower maximum, for example 253 − 1, and the engine needs no change for it.

CNT-3. The engine API change (Call)

pub fn Budget::parse(instructions : Int64) -> Budget raise LimitError // unchanged signature
pub fn Budget::instructions(self : Budget) -> Int64                 // was Int32

The extern wamr_call takes the budget as Int64, and the stub extism_wamr_call takes it as int64_t. MoonBit's Int64 is int64_t in the native FFI on every platform. The path uses no C long, which has 32 bits on Windows (LLP64). No call path is cast to int.

Tests

The fixture spin_n(n) runs a loop of n iterations. Its cost is k × n + c metered instructions: on macOS arm64 k is 3, and c is 2 with computed goto and 3 with the switch dispatch (as MSVC builds it). So the test measures k and c with a binary search on small budgets, checks the formula at n = 1000, and then selects the n whose cost is more than 231 + 1,000,000. The call completes with a budget of exactly that cost, and it stops with BudgetExhausted with 1 instruction less. With the int counter, the second call does not stop, because the value wraps to a negative count.

The two long calls take about 3 s on macOS arm64. The whole test took about 20 s on windows-latest with MSVC (run 42549618598), below the limit of 60 s for each test in that workflow. The test runs in mise run test on native, in the switch-dispatch step of CI, and in the manual Windows MSVC workflow.

Risks and trade-offs

RiskMitigation
A 64-bit decrement is slower on a 32-bit hostThe engine supports 64-bit hosts only. On macOS arm64, a loop of 700,000,000 iterations took 1506 to 1576 ms before and 1513 to 1537 ms after
A new vendor run loses the patchThe patch is in scripts/vendor-wamr.mbtx, and a hunk that does not match its upstream text once stops the vendor run
Upstream adds a different 64-bit APIAt the next WAMR upgrade, use the upstream API and remove the patch
The archive of this change before host-extism-plugins fails, because the requirement is not yet in openspec/specs/Archive host-extism-plugins first

Migration plan

Release 0.3.0 after the maintainer approves it. A caller that reads Budget::instructions changes its type to Int64. finos/morphir-moonbit calls only Budget::parse, and then moves CallBounds.instructions and --instructions to Int64 in its own pull request.

Open questions

  • The maintainer selects the maximum: the Int64 maximum in this library (CNT-2), with a lower maximum in a consumer where it needs one. The design of this change does not depend on the answer.
  • An upstream pull request with CNT-1 and the classic interpreter needs the maintainer's approval.
