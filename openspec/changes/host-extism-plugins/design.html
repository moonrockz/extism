Context

See proposal.md for the motivation. The repository has the canonical moonrockz setup and four empty packages. This design comes from the approved design of host-extensions-as-workers in finos/morphir-moonbit (decisions EXT-1, EXT-2, EXT-3, WASM-1, WASM-4 and the section "The moonrockz/extism repository"). Decisions that come from there are labelled Owner. Decisions that this design adds are labelled Call.

Facts from the upstream sources that shape the design:

  • Upstream Extism does not run its kernel as host code. The kernel is a no_std Rust crate compiled to WASM (runtime/src/extism-runtime.wasm, 3,474 bytes, 16 initial pages of memory). Its exports are memory, the 20 kernel functions, __data_end, __heap_base and the extism_context externref global, which kernel/build.sh merges in with wasm-merge --enable-reference-types. The Go, Java, Erlang and WAMR SDKs embed the same file.
  • The JavaScript SDK (src/call-context.ts) has a second kernel written in JavaScript, so its allocation and limits differ from the other SDKs.
  • extism/wamr-sdk registers each kernel import as a WAMR native symbol in extism:host/env; each native function calls the kernel instance with wasm_runtime_call_wasm_a.
  • Before the first call, upstream initializes the guest runtime: hs_init (after _initialize) for Haskell, else __wasm_call_ctors, else _initialize.
  • WAMR WAMR-2.4.5 has instruction metering in the fast and the classic interpreter (WAMR_BUILD_INSTRUCTION_METERING, wasm_runtime_set_instruction_count_limit), a maximum memory size per instantiation (wasm_runtime_instantiation_args_set_max_memory_pages) and wasm_runtime_terminate. Its CMake selects an assembly invokeNative per architecture, .asm (MASM) on Windows MSVC, or invokeNative_general.c. On x86_64 and aarch64, invokeNative_general.c reads the uint64 register array as uint32 cells, so a native with an i64 parameter gets a wrong value. A native that is registered with wasm_runtime_register_natives_raw gets its arguments as an array of cells and needs no invokeNative.
  • WAMR writes the resolved native of each import into the import entries of the compiled module, and its native registry is process-global. A native function finds its calling instance through the execution environment, and wasm_runtime_get_custom_data gives the data that the embedder put on that instance.
  • wasm_runtime_terminate sets a flag that the fast interpreter reads at its CHECK_SUSPEND_FLAGS points only when WAMR is built with WASM_ENABLE_THREAD_MGR=1.
  • The upstream kernel: the root record is at offset 1 and is 64 bytes, so the first block is at offset 65. A block header is 12 bytes. With bounds checks, a load or store of n bytes at offset p runs when p + n − 1 ≥ 64 and p + n − 1 ≤ the memory size; the access traps when p + n is larger than the memory size. The Rust shadow stack is below 1 MiB (__heap_base), in the same pages as the root record.

Goals and non-goals

Goals: one kernel artifact for every engine; a plugin API that runs any conformant Extism plugin and gives the embedder the decision for every authority; a WASI sandbox written once; bounds that are reported as they are enforced; no prebuilt library and no Rust toolchain.

Non-goals: a full Extism SDK feature set in the first version (plugin download, manifest files, pooling, cancel handles shared across threads); process or thread isolation, which stays with the embedder; engine performance beyond the EXT-2 gate.

One call, from manifest to output

An embedder has the bytes of a plugin and wants to call its handle export with a JSON request.

  1. The embedder makes a Manifest with the bytes, the limits, the policy, its registered host functions and, if the plugin needs it, the WASI sandbox with a clock, a random source and two sinks.
  2. Plugin::load reads the import section of the module. Each import must be one of the kernel functions, an Extism host function, a registered host function or, with the sandbox, a WASI preview 1 function. The first other import refuses the load and names it.
  3. The plugin API instantiates the embedded kernel bytes on the engine, with the kernel memory ceiling. Then it instantiates the plugin with the plugin memory ceiling and binds its imports: kernel imports to the kernel instance (BND-1), host functions to MoonBit closures that see a CallContext.
  4. Before the first call, the plugin API runs the guest runtime start-up (_initialize or the others).
  5. Plugin::call(self, "handle", input) calls the kernel's reset, allocates the input in kernel memory, calls input_set, and calls handle with the instruction budget and the deadline.
  6. When handle returns 0 and no error is set, the plugin API reads output_offset and output_length and copies the output bytes out of kernel memory. An error is set, as upstream decides, when error_get gives a handle that is not 0 and the length of that handle is not 0. Otherwise the call fails with a typed error. A proc_exit(0) with no error set is a successful call that returns its output.

Decisions

PKG-1. One module, four packages; the sandbox does not import the engine (Call)

One published module, moonrockz/extism, holds the four packages, so that a consumer pins one version. The package names are the ones in the Morphir design. The kernel package holds only bytes and ABI values. The wasi package must build on all four targets, but the engine supports only native and js, so wasi defines a GuestMemory trait (read and write bytes, little-endian integers, size) and the engine implements it for an instance's memory. The plugin API joins them.

Alternatives. One package: a consumer that needs only the engine (the Morphir morphir-bytes-v1 adapter) would get the plugin API too. wasi imports engine: then wasi is native and js only, against the approved target table.

KRN-1. The kernel is Zig, compiled to wasm32-freestanding with an explicit CPU (Owner, details Call)

The kernel is about 300 lines of Zig with no libc and no allocator from the standard library. It follows the upstream memory layout exactly: the module declares 16 initial pages; the root record (initialized flag, bump position, tracked length, error, input and output offsets and lengths) is the 64 bytes at offset 1, so the first block header is at offset 65; a block header is 12 bytes (a status of unused, active or free, a size and a used length); a handle is the offset of a block's data. The arithmetic wraps, as the upstream release build does.

It keeps the upstream bounds rule (the default bounds-checking feature of the Rust crate): a load or store of n bytes at offset p runs only when p + n − 1 ≥ 64 and p + n ≤ the memory size. Otherwise a load returns 0 and a store does nothing; neither traps. On every offset where upstream does not trap, the result is the upstream result. Where upstream traps because p + n is larger than the memory size (for example load_u8 at the memory size), or because a block walk reads past the memory, the Zig kernel returns 0 or does nothing. Where upstream traps, the differential test of KRN-2 checks that the Zig kernel traps or gives 0, and then starts both kernels again.

The kernel has no stack and no data in its linear memory: the module has no data segment, the build sets the stack size to 0, and no kernel function takes the address of a local or returns a value through memory (the block functions return offset 0 for no block, not an optional). So a plugin store_* can change only the root record bytes that upstream also exposes and the blocks; it cannot reach a stack or static data, because there is none. A test reads the kernel bytes and checks that there is no data section and that no function body reads or writes a global.

cd kernel && zig build    # zig-out/bin/kernel.wasm
# build.zig: wasm32-freestanding, cpu mvp+mutable_globals+sign_ext, ReleaseSmall, strip, no entry,
# initial memory 16 pages, stack size 0, exports: memory and the 20 kernel functions only

The CPU is mvp+mutable_globals+sign_ext. The Zig default for wasm32 also enables reference types, bulk memory and other features; an explicit list makes sure that the kernel needs no feature that an engine might lack, and that a Zig upgrade does not change the feature set. mise run build:kernel writes pkgs/extism/kernel/kernel_bytes.mbt with the bytes and their SHA-256; mise run check:kernel builds into _build/ and fails when the bytes differ. CI runs the check on Linux and macOS so that a host-dependent build shows.

Settled. The Zig kernel is a settled maintainer decision (Damian Reeves, 2026-10-30), made again after the review of the implementation. A change to it needs a new OpenSpec change that the maintainer approves first. The reasons:

  • The repository builds the kernel from its own source with the pinned Zig, and fixes it without a Rust toolchain or a new upstream release.
  • The kernel returns 0 or changes nothing where upstream traps, so a plugin with a bad pointer fails that call and is not made unusable.
  • The differential test of KRN-2 keeps the kernel equal to upstream. Its generated sequences found three differences, which are fixed and have Zig tests.

Alternatives. Embed upstream extism-runtime.wasm. Its source is Rust, which needs a Rust toolchain to rebuild, it traps where the Zig kernel gives 0, and it would put third-party bytes in the published package. When EXT-3 rejected it, it also needed reference types that an engine could lack; both engines now have reference types, and the differential test runs the file on both, but the other reasons stand. A kernel in MoonBit: every byte that a plugin reads would cross into host code on every engine. Both were rejected in EXT-3, and the rejection of upstream's file was confirmed on 2026-10-30.

KRN-2. The kernel is tested against upstream, call for call (Call)

Zig tests check the allocator and the bounds checks. A differential test in tests/ runs recorded call sequences (allocate, store, load, free, reuse, input, output, error, reset, out of memory) on the Zig kernel and on upstream extism-runtime.wasm, both on the js engine, and compares every result and every live block. The upstream file is a test fixture with its BSD-3-Clause license and SHA-256; it is not in the published package. The js engine accepts its externref global, so the fixture runs unchanged.

The sequences are generated with the handles that upstream's alloc gives, so later calls reach live and freed blocks. They include store_u64 and input_load_u64, the offsets at the edge of the root record and of 64-bit accesses (56, 57, 63, 64), values near 2^64, and addresses at the end of memory. Where upstream traps, the test checks that the Zig kernel traps or gives 0, starts both kernels again with the calls before the trap, and goes on. These sequences found three upstream details that the Zig kernel now follows: the first initialization clears 144 bytes after the root record (upstream's write_bytes counts MemoryBlock values, not bytes); the block walk adds in 32 bits, as wasm32 pointers do, so a size that a plugin forges wraps around; and a new block is placed at the position modulo 2^32.

ENG-1. The engine API (Call)

The engine package gives one API with two backends. Names are subject-first and values are typed:

pub enum Value { I32(Int); I64(Int64); F32(Float); F64(Double) }
pub enum ValueType { I32; I64; F32; F64 }
pub struct Signature { params : Array[ValueType]; results : Array[ValueType] }
pub struct PageCount(..)     // PageCount::parse(Int) raise LimitError; 1 to 65536
pub struct Budget(..)        // instructions per call, 1 to 2147483647 (the C int of WAMR)
pub struct Deadline(..)      // milliseconds per call, more than 0
pub enum Feature { Simd; Threads; Memory64; ExceptionHandling; Gc; TailCall; MultiMemory; Unknown(String) }
pub enum Bound { Enforced; NotEnforced }

pub fn Feature::scan(Bytes) -> Array[Feature] raise EngineError   // pure; both engines use it

pub fn Engine::default() -> Engine                       // WAMR on native, WebAssembly on js
pub fn Engine::bounds(self) -> Bounds                     // memory, budget, interruption
pub fn Engine::compile(self, Bytes) -> Module raise EngineError
pub fn Module::imports(self) -> Array[ImportDescriptor]
pub fn Module::exports(self) -> Array[ExportDescriptor]
pub fn Module::instantiate(self, Imports, memory_ceiling~ : PageCount, budget? : Budget, deadline? : Deadline) -> Instance raise EngineError
pub fn Instance::call(self, String, Array[Value], budget? : Budget, deadline? : Deadline) -> Array[Value] raise CallError
pub fn Instance::memory(self) -> Memory?                  // implements @wasi.GuestMemory
pub fn Instance::export_function(self, String) -> Function?

Imports holds entries of a module name, a field name, a Signature and either a MoonBit closure ((Caller, Array[Value]) -> Array[Value] raise HostError) or an exported Function of another instance. Caller gives the calling instance's memory. Errors are closed enums: EngineError (Invalid, FeatureUnsupported(Feature), LinkError, CeilingBelowInitial, Start(CallError)) and CallError (Trap(TrapKind), BudgetExhausted, Interrupted, MemoryLimit, Host(HostError), UnknownExport). The engine does not know Extism.

Imports are bound per instance. Two instances of one compiled module can have different closures and different exported functions for the same import, so two plugins from the same bytes each reach their own kernel.

Feature::scan is a pure MoonBit pass over the module bytes (section headers, limits flags and the opcodes of each function body). Both engines run it before they compile, so a module that needs a feature that the engine lacks fails with FeatureUnsupported and the feature name on native and on js. Each engine gives its set of supported features.

A ceiling smaller than the initial pages of the module's memory is refused at instantiation with CeilingBelowInitial, which holds both page counts, on both engines.

The prepared module. Both engines compile the module after a pure rewrite, @binary.Module::prepare: it removes the start section and exports the start function under the reserved name __moonrockz_extism_start, and it exports memory 0 under the reserved name __moonrockz_extism_memory. No index changes. A module that exports a name with the prefix __moonrockz_extism_ is refused. So no guest code runs inside the engine's instantiation: the instantiation makes the instance, sets the Caller of its host functions, and then calls the start function as a call with the budget and the deadline that the caller gives. A start function that fails makes the instantiation fail with Start and the call error. On js, the memory export lets the host reach the memory of a module that does not export memory, as on native. The exports that the rewrite adds are not in Module::exports.

The engine meters guest instructions only. The work of a host function, for example a WASI call or an Extism host function, and the block walks of the kernel's forwarders on native, which run in another instance with no budget, count against no instruction budget; the deadline bounds them.

A memory.grow that the ceiling refuses returns -1 to the guest, and the engine records the refusal for the current call. When a call then fails, the error is MemoryLimit, not the trap that followed. On native the record comes from WAMR's enlarge-memory error callback. On js the memory rewrite of ENG-3 also sends each memory.grow through a function that it appends to the module, which records a result of -1.

ENG-2. The native engine is the WAMR fast interpreter, vendored and built from C source (Owner, build Call)

The engine vendors the C source of WAMR-2.4.5 that the fast interpreter needs (iwasm common, interpreter, shared platform and utils, mem-alloc) under pkgs/extism/engine/wamr/, with its license and an UPSTREAM.md that records the tag, the commit and the file list. The build settings follow WAMR's CMake: INTERP=1, FAST_INTERP=1, AOT=0, JIT=0, LIBC_BUILTIN=0, LIBC_WASI=0 (the sandbox is ours), BULK_MEMORY=1, REF_TYPES=1, INSTRUCTION_METERING=1, THREAD_MGR=1 (see ENG-4), MULTI_MODULE=0, SIMD=1 and SIMDE=1. The vendored tree keeps WAMR's LICENSE (Apache-2.0 WITH LLVM-exception) and ATTRIBUTIONS.md, and pkgs/extism/README.md has a third-party note.

SIMD. The native engine supports the fixed-width SIMD proposal, as the js engine does, so the feature set of both engines is simd. MoonBit guests, for example the portable Morphir MEP extension, use v128 through moonbitlang/x/crypto, and moonc has no flag to turn it off. WAMR's fast interpreter runs SIMD through the SIMDe headers (WASM_ENABLE_SIMDE). The engine vendors the headers that simde/wasm/simd128.h includes, from SIMDe v0.8.2 (MIT, the version that WAMR's CMake fetches), under wamr/simde/ with SIMDe's COPYING. Upstream WAMR turns SIMDe off on Windows; the third patch below makes the one construct that MSVC does not compile portable, and the Windows MSVC run proves the build. A SIMD probe module gives the same lanes on both engines.

Every host import, the kernel forwarders, the WASI functions and the embedder's functions, is registered with wasm_runtime_register_natives_raw. A raw native gets its arguments as an array of 64-bit cells and writes its results into the same array, so no invokeNative runs on any platform: no assembler is needed, Windows MSVC needs no MASM, and the invokeNative_general.c fault with i64 arguments cannot occur. That file is not vendored.

WAMR's native registry is process-global, and the resolution is written into the import entries of the compiled module. So the C stub registers one generic raw trampoline per import signature and name once per process, and binds nothing per instance in WAMR. When an instance is made, the stub puts its import table (the MoonBit closure or the exported function of another instance for each import) on the instance with wasm_runtime_set_custom_data. A trampoline finds the calling instance from its execution environment, reads that table with wasm_runtime_get_custom_data and calls the entry for its import. A test loads two plugins from one compiled module and checks that each reaches its own kernel.

Local patches. The vendored source is the upstream source, with its includes made relative, except for the patches in this list. scripts/vendor-wamr.mbtx applies each one when it vendors WAMR, fails when the upstream text does not match exactly once, and lists it in wamr/UPSTREAM.md.

  • core/iwasm/interpreter/wasm_interp_fast.c, function wasm_interp_call_func_bytecode, the WASM_ENABLE_LABELS_AS_VALUES == 0 dispatch loop: the loop runs CHECK_INSTRUCTION_LIMIT() before each opcode. Reason: a compiler with no computed goto (MSVC) builds the switch dispatch, and upstream calls CHECK_INSTRUCTION_LIMIT only in the computed-goto FETCH_OPCODE_AND_DISPATCH macro, so the instruction budget is not enforced there. Without the patch, "Runaway loop on native" does not end on Windows MSVC (run 41120275074) and in a build with WASM_ENABLE_LABELS_AS_VALUES=0; CI runs the engine tests in that build on Linux. Upstream fixed it after WAMR-2.4.5 in commit ea5dd88e (pull request #5141, issue #5140); the patch goes at the next WAMR upgrade.
  • core/iwasm/interpreter/wasm_interp_fast.c, the SIMDe code: the macro SIMD_V128_TO_SIMDE_V128 calls a static inline function instead of a GNU statement expression. Reason: MSVC does not compile statement expressions, and upstream builds SIMDe on no Windows platform (build-scripts/runtime_lib.cmake, at WAMR-2.4.5 and at main f8ed1f44).
  • core/iwasm/interpreter/wasm_runtime.c, function execute_post_instantiate_functions: the instantiation does not look up __post_instantiate and __wasm_call_ctors; it runs only the wasm start function. Reason: the plugin runs the guest's start-up exports itself, as upstream Extism does (PLG-1), and WAMR ran the constructors a second time, with no budget and no deadline. No WAMR setting or API skips these lookups. The test "Constructors run once" fails without the patch.

mise run check:wamr compares each vendored file with the SHA-256 that wamr/UPSTREAM.md gives for it, after the include rewrite and the patches, and fails on a changed, missing or unlisted file. CI runs it in the lint job.

pkgs/extism/engine/wamr/build.zig holds the source list and the defines, the same as the CMake selection. It builds and tests WAMR alone with Zig for every CLI platform in CI. It also writes the native-stub list and the stub-cc-flags of the engine's moon.pkg; a check fails when they differ. A consumer then builds the engine with its configured C compiler: Zig through zig-cross in finos/morphir-moonbit, MSVC on Windows. The first task of the engine group proves this on a fresh consumer on every platform, before other engine work depends on it.

Alternatives. A Moon pre-build step that runs zig build and links a static library: every consumer would need Zig on PATH at build time, and Windows MSVC linking of a Zig-built archive is less known. It is the fallback if native-stub cannot take the source list. The Wasmtime C API is the engine fallback of the EXT-2 gate.

ENG-3. The js engine is WebAssembly; the memory ceiling is a module rewrite (Owner, details Call)

The js backend uses WebAssembly.Module and WebAssembly.Instance through extern "js", so it runs on Node.js and browsers with no package. js has no instruction metering and cannot stop a synchronous call on the same thread, so its bounds report gives the budget and interruption as not enforced. The memory ceiling is enforced by a pure MoonBit function that rewrites the memory section's maximum to the ceiling before compile, as finos/morphir-moonbit does today. Imported memories are refused, and a second memory is the feature multi-memory, which both engines refuse with the same error. The same rewrite appends one function and one global to the module: each memory.grow in a function body calls the appended function, which runs memory.grow and sets the global when the result is -1. Appended functions and globals take the next free indices, so no other index changes. The engine reads and clears the global for each call to report MemoryLimit.

ENG-4. Native limits: maximum pages, metering and a watchdog deadline (Call)

On WAMR the memory ceiling is the instantiation argument for the maximum pages, also when the module declares no maximum. The budget is wasm_runtime_set_instruction_count_limit on the plugin's execution environment before each call; it is a C int, so a Budget is at most 2147483647. Kernel calls through the forwarders run on the kernel instance's own execution environment, so they do not count against the plugin's budget.

The deadline is a watchdog thread in the C stub that calls wasm_runtime_terminate on the instance when the deadline passes. WAMR is built with WASM_ENABLE_THREAD_MGR=1, so that the fast interpreter sees the terminate flag at its CHECK_SUSPEND_FLAGS points, also in a tight loop. The watchdog is always cancelled and joined before Instance::call returns: after a normal return, a trap, an exhausted budget or a host error. The watchdog decides to fire, and records that it fired, under its lock; the call stops and joins it before it reads the exception. When the watchdog fired after the guest returned, the call keeps its results and clears the exception, so the next call does not see the termination. A test delays the stop of the watchdog after the return to make this race certain. Each watchdog thread counts itself at its start and at its end, so a test that finds the count above 0 after the calls finds a thread that was not joined. There is no fallback that reads the metering counter, because WAMR keeps it in a local of the interpreter loop.

The host functions of an instance have a range of ids in a table in the MoonBit stub. The table refers to no instance: the trampoline gives the host function its calling instance. The finalizer of an instance records its range as freed, and the next instantiation removes those entries, so loaded and dropped plugins do not stay in memory. Each instance holds a reference on its module in the C stub, so WAMR unloads the module after its last instance.

Where the stub cannot start a thread, or where THREAD_MGR is not viable on a platform, the bounds report gives interruption as not enforced by the engine, and only the instruction budget bounds a call there. The Morphir host still ends its worker process at its own deadline.

The engine maps the WAMR exception text to BudgetExhausted, Interrupted or a TrapKind in the C stub, so MoonBit code never matches messages.

BND-1. Kernel binding per engine (Owner)

On js the kernel instance's exports are the plugin's extism:host/env imports, so a kernel call is a direct WASM-to-WASM call. On WAMR each kernel import is a native forwarder that calls the kernel instance, the pattern of extism/wamr-sdk, registered raw as ENG-2 says. WAMR multi-module linking is measured in the EXT-2 gate with a separate gate build that sets MULTI_MODULE=1, because the engine build fixes MULTI_MODULE=0; it replaces forwarding only if it is faster and works with the fast interpreter, and that needs a change to ENG-2. A native C-ABI build of the same Zig kernel is added only if the gate shows that forwarding is too slow; both builds then run the same Zig tests.

PLG-1. The plugin API (Call)

pub fn Manifest::limits(self, Limits) -> Manifest
pub fn Manifest::policy(self, Policy) -> Manifest
pub fn Manifest::register(self, HostFunction) -> Manifest raise ManifestError
pub fn Manifest::wasi(self, @wasi.Sandbox) -> Manifest
pub fn Plugin::load(Manifest, engine? : @engine.Engine) -> Plugin raise LoadError
pub fn Plugin::has_function(self, ExportName) -> Bool

pub fn Plugin::bounds(self) -> @engine.Bounds

pub fn HostFunction::new(Namespace, FunctionName, @engine.Signature,
  (CallContext, Array[@engine.Value]) -> Array[@engine.Value] raise HostError) -> HostFunction

pub fn CallContext::allocate(self, Bytes) -> Handle raise MemoryError

Manifest builder steps return a new value. Namespace, FunctionName, ExportName and Handle are validated types. register refuses a name in extism:host/env and a name that is already registered. The import check of a load is a pure function over the import descriptors and the manifest, tested without an engine.

A call fails with a typed CallError: Plugin(code, text) for a non-zero return or a set error, Exit(code) for a non-zero proc_exit, Denied(function) for a denied Extism host function (for http_request it also holds the method and the URL of the refused request), HostFunction(name, message), MemoryLimit(memory) for a refused grow of the plugin or the kernel memory, Engine(@engine.CallError) for a trap, an exhausted budget or an interruption, Initialization and UnknownExport. An alloc that the kernel refuses at its ceiling is a refused grow of the kernel memory, so a call that then fails reports MemoryLimit(Kernel).

The same manifest and input give the same output bytes, error kinds and host function calls on native and js, except where an outcome comes from a bound that only one engine enforces (the instruction budget and the deadline).

The table is data in the wasi package, one entry per preview 1 function with its signature, so a test can check that every function of the pinned wasi_snapshot_preview1 witx is linked. The WAMR socket extensions (sock_open, sock_bind and others) are not preview 1 and are not linked; the WAMR build has LIBC_WASI=0, so WAMR links no WASI function of its own.

GATE-1. The EXT-2 qualification gate (Owner)

The gate runs directly after the WAMR build spike (task 2.1), before any other work builds on WAMR. It uses a minimal engine-level harness, not the plugin API: the embedded kernel, the raw-native kernel forwarders of BND-1, a stub WASI that answers every function with ENOTCAPABLE, and stubs for the four extism:host/user morphir_* functions.

mise run qualify:engine fetches the Morphir Python extension 0.4.2 module by a pinned URL and SHA-256 into _build/, and runs the compile request of the Morphir fixture through handle with metering on and a budget of 1,000,000,000 instructions. It records the time of each call and the instructions used. A separate gate build with MULTI_MODULE=1 runs the same request with multi-module linking in place of the forwarders. The gate passes when the compile finishes within 30 seconds on the slowest qualified platform. The results go to bead morphir-ukvn.5.64.36.4 as a comment. If the gate fails, the engine group switches to the Wasmtime C API behind the same engine API, and this design is updated first.

REL-1. Release (Call)

The first release is 0.1.0, published to Mooncakes by a release workflow that runs only after the maintainer approves the version change, adapted from moon-lander's release.yml. A fresh module outside the repository pins the exact version and builds on native and js before the GitHub release is made.

Risks and trade-offs

RiskMitigation
WAMR's interpreter is too slow for Python compilesGATE-1 measures the real fixture first; the Wasmtime C API is the named fallback behind the same engine API.
Moon's native-stub cannot take the WAMR source list, include paths or definesENG-2's first task proves it on a fresh consumer on every platform; the pre-build static library is the fallback.
wasm_runtime_terminate is seen only at check points that need WAMR's thread managerThe build sets THREAD_MGR=1, and the deadline scenario is a test on every platform. Where the thread manager is not viable, the bounds report gives interruption as not enforced, and the embedder ends its worker.
A watchdog thread outlives its callThe stub cancels and joins the watchdog on every return path; a test runs many short calls and checks that no thread is left.
Zig builds of the kernel differ between hosts or Zig releasescheck:kernel runs on Linux and macOS; Zig is pinned with finos/morphir-moonbit's pin.
The Python module needs a feature that the fast interpreter build lacksGATE-1 records the feature error with its name. SIMD is enabled for MoonBit guests, and the gate runs with it on every platform.
A conformant plugin needs a WASI answer other than an errorThe plugin fails with its own diagnostic. Fixture plugins built with upstream PDKs exercise the start-up calls; a new answer needs a reviewed change to WASI-1.
The vendored WAMR source makes the Mooncakes archive largeVendor only the fast-interpreter files; record the archive size in the release task.
The js engine cannot stop a runaway callThe bounds report says so; embedders run plugins in a worker and terminate it, as finos/morphir-moonbit does.

Migration plan

None: the packages are new. finos/morphir-moonbit adopts the first published version in its group 5.

Open questions

  • The exact default ceiling of kernel memory. The spec fixes 4096 pages for any instance; a smaller kernel default can come later without a spec change to the plugin memory.
  • Whether the native engine keeps one engine runtime per process or per plugin. This does not change the API.
